# HASHING.md — how a CertiChain certificate hash is computed

Everyone (certificate service, issuer dashboard, verify page, tests) MUST produce the same hash for the same certificate. If this spec and your code disagree, fix your code.

## 1. Certificate JSON
Fields (all values are **strings**, no numbers/booleans/nulls, so every language serializes them identically):

| Field | Example |
|---|---|
| `@context` | `https://certichain.example/context/v1` |
| `type` | `EventCertificate` |
| `id` | `https://certichain.example/c/0001` |
| `event` | `{title, date, organiser}` |
| `participant` | `{name}` (no email, no student number in the hashed JSON) |
| `issuedBy` | `{clubName, wallet}` |
| `issuedOn` | `YYYY-MM-DD` |
| `salt` | 32 hex chars (16 random bytes), unique per certificate |

## 2. Canonical form
1. Sort object keys alphabetically at every level (recursive).
2. No whitespace anywhere (separators are `,` and `:`).
3. UTF-8 bytes, no escaping of non-ASCII characters (Turkish letters stay as they are).
4. No trailing newline.

This matches RFC 8785 (JCS) for string-only data.
- Python: `json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False)`
- Node.js: use the `canonicalize` npm package (RFC 8785).

## 3. Hash
`hash = SHA-256(canonical UTF-8 bytes)`, written as `0x` + 64 lowercase hex chars. This is the `bytes32` passed to `issue` / `issueBatch` / `verify`.

## 4. Salt
- Generated by the certificate service with a cryptographically secure RNG (`crypto.randomBytes(16)`).
- Stored inside the certificate JSON (so it is part of the hash) and kept off chain with the certificate file.
- Never reused. Never written to the chain.

## 5. Worked example (everyone must reproduce this)
Input certificate, canonical form:

```
{"@context":"https://certichain.example/context/v1","event":{"date":"2026-12-05","organiser":"IKU Computer Club","title":"Git Workshop"},"id":"https://certichain.example/c/0001","issuedBy":{"clubName":"IKU Computer Club","wallet":"0x7B40B303bD39685Ed6f7A236ff7E8F21D5D6B860"},"issuedOn":"2026-12-05","participant":{"name":"Ayse Yilmaz"},"salt":"9f2c4a1be07d33c85a6e1f40d2b9c7a8","type":"EventCertificate"}
```

Expected hash:

```
0x1cc9450abb434d4132d723e323ae36c72363f5d5b14c4096cc999a7d13c074cc
```

Test: feed the JSON above (in any key order) into your code. If you do not get this exact hash, something differs (key order, whitespace, encoding, salt handling).

## 6. Verify by PDF upload
The verify page recomputes the hash from the certificate JSON, not from the PDF's pixels. So the PDF must carry the certificate JSON (embedded file attachment or the JSON stored by the service and fetched via the QR link `id`). Decide which one in the team chat and write it here.
