# HASHING.md — How a CertiChain Certificate Hash Is Computed

Everyone (certificate service, issuer dashboard, verify page, tests) MUST produce the same hash for the same certificate.

## 1. Certificate JSON (W3C VC v2.0 JSON-LD)
Built by `service/src/certificateBuilder.js` and validated against `schema/`:

| Field | Type / Format | Description |
|---|---|---|
| `@context` | Array | W3C VC v2, PROV-O, and `https://certichain.iku.edu.tr/schema#` context |
| `id` | String (URI) | Unique certificate URN (e.g. `urn:uuid:...`) |
| `type` | Array | `["VerifiableCredential", "ParticipationCertificate"]` |
| `issuer` | Object | `{ id: "did:pkh:eip155:11155111:<wallet>", name: "<clubName>" }` |
| `validFrom` | ISO-8601 String | Issuance timestamp |
| `credentialSubject` | Object | `{ id, recipientName, recipientEmail, eventTitle, eventDate, hours }` |
| `wasAttributedTo` | Object | `{ id: "<issuerDid>" }` |
| `wasGeneratedBy` | Object | `{ type: "prov:Activity", name: "<clubName> - <eventTitle>" }` |
| `salt` | 32-char hex string | 16 random bytes (`crypto.randomBytes(16)`), unique per certificate |

## 2. Canonical Form (RFC 8785 / JCS)
1. Sort object keys alphabetically at every level (recursive), preserving array order.
2. No whitespace anywhere (separators are `,` and `:`).
3. UTF-8 bytes without escaping non-ASCII characters.
4. No trailing newline.

Implemented identically in `service/src/certificateHasher.js` (`canonicalizeJson`) and `web/verify.html` (`canonicalJson`).

## 3. Hash
`hash = SHA-256(canonical UTF-8 bytes)`, formatted as `0x` + 64 lowercase hex characters (`bytes32` in `CertificateRegistry.sol`).

## 4. Salt
- Generated by `certificateBuilder.js` using `crypto.randomBytes(16)`.
- Included inside the certificate JSON (part of the hash) and never stored on-chain.

## 5. Worked Example (Verified Against `certificateHasher.js`)
Canonical JSON input:

```text
0x7893cc0d9d8ef11eeeea8226c0722b660e236f33739ff93d5c7ed9f4d41515f2
```

## 6. Verify by File Upload / QR Link
- Scanning the QR code opens `web/verify.html?hash=0x...` and queries `CertificateRegistry.verify(hash)` directly on Sepolia.
- Every PDF embeds the certificate JSON as the attached file `certichain-certificate.json`. Uploading the **PDF** (or that JSON) on `web/verify.html` reads the JSON, canonicalizes it in the browser and recomputes the identical SHA-256 hash locally (story S7). An edited file gives a different hash, so the page shows ❌ Not found.
